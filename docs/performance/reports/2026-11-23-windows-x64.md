# Renderer benchmark report · 2026-11-23

Merman's benchmarks help us choose where to investigate rendering costs. A renderer can accept the same Mermaid source and choose different node sizes, edge routes, fonts and SVG structure. The observations below apply to the named products, workloads and machines.

- **Coverage.** The Node survey includes 145 calls in 72 scenarios, with 37 single-example family baselines.
- **Warm timings.** 8 of 8 scenario and peer pairs have every scheduled round. The faster product changed between rounds in 6 of those pairs.
- **Native limits.** 28 of 32 Flowchart topologies produced SVG at Merman's default layout budget.

Node, CLI and browser measurements use published Merman 0.11.0 artifacts. The browser comparison uses the npm package @mermanjs/web with the v0.11.0 Playground and Mermaid.js 12.3.0. The native layout work probe uses a local benchmark checkout.

## What the renderers aim to do

| Product | Design and public operation |
| --- | --- |
| Merman | A headless Rust renderer aiming for compatibility with a pinned Mermaid.js release across syntax, configuration, themes and SVG structure. The Rust library, Node binding and CLI expose different operation boundaries. |
| Pele | An independent renderer of Mermaid syntax with its own layout and visual style. Its public `render` call returns a themeable SVG synchronously. |
| Mermaid v13 | The upstream v13 package exposes a headless Node rendering API. The exact package version and the diagram plugins available to the consumer matter when interpreting coverage. |
| Mermaid CLI (`mmdc`) | The upstream command-line tool uses Mermaid in a browser process to produce files. Startup, font selection and painting can contribute to the cost of a PNG export. |

[Merman compatibility](https://github.com/Latias94/merman#rendering-quality-and-performance) · [Pele design](https://github.com/obsidianmd/pele/tree/1.13.0#compatibility) · [Mermaid v13](https://github.com/mermaid-js/mermaid-v13) · [Mermaid CLI](https://github.com/mermaid-js/mermaid-cli)

## Merman layout work

On Windows AMD64, the native library observed 32 of 32 planned Flowchart topologies. At the default budget, geometry completed on **29/32** and public SVG on **28/32**. Work units count operations charged by Merman's layout budget. The minimum is verified on the geometry writer at adjacent passing and failing ceilings. **How to read layout work:** geometry and SVG counts are successful results / observed cases; more means broader completion under this budget. 'Work limit' and 'Source edge limit' are different causes. Fewer minimum geometry units means a lower charged-work threshold for that source, not a measured rendering-time advantage.

## Interpreting the comparison

Use a row that resembles your application. Rendering one preview, updating an existing engine and starting a CLI for each file incur different costs. Successful artifact and label checks cover the features asserted for those inputs. Visual fidelity, clipping, accessibility and interaction need their own checks. A performance difference between products can suggest an experiment. Establish its cause by comparing Merman revisions on the same source, settings and output contract.

For native Rust peers and comparisons between Merman revisions, consult the dedicated measurements. The [portable measurements](2026-11-23-windows-x64.json) contain the sample units, workload fingerprints and observations used here. To regenerate this Markdown from the adjacent receipt, run the following from a checkout that contains the report generator.

Use the path of the linked JSON in place of `path/to/measurements.json`. Add `--check` to verify the adjacent Markdown. The JSON records the plan and product fingerprints for each measurement. This snapshot has no public raw-bundle link.
