Status: engineering gates implemented; final-artifact evidence and legal review remain release duties
Audit date: 2026-07-20
Repository license expression: `MIT OR Apache-2.0`
Mermaid behavior baseline: `mermaid@11.16.1`

> This is an engineering audit, not legal advice. It records primary-source evidence, packaging
> expectations, and release checks. It does not determine whether a license is enforceable, whether
> a work is derivative, or whether a particular distribution model satisfies every legal obligation.
> A maintainer or qualified counsel must resolve those questions when the engineering evidence is
> insufficient.

## Method

The unit of review is a released artifact, not the repository as a whole. A declaration in a source
manifest does not prove that the corresponding license text, notices, source offer, or dependency
materials are present in the file that users actually receive.

For each release artifact, this audit keeps four facts separate:

1. **Declared license**: the expression in package metadata.
2. **Concluded license**: the license supported by upstream source and package evidence.
3. **Distributed content**: code, generated code, fonts, native libraries, WebAssembly, and assets
   physically present in the artifact.
4. **Required evidence**: license texts, notices, provenance, metadata, and source availability that
   must accompany that distributed content.

Only official specifications, registry documentation, and upstream repository or release metadata
are authoritative sources in this document. A dependency scanner is useful evidence, but its output
does not replace inspection of source headers, license files, or the final archive.

Evidence states used below are:

- **Verified source**: an official specification or exact upstream license/package file was read.
- **Repository observation**: a fact observed in this checkout; it must be rechecked at release tag.
- **Release gate**: evidence that must be produced from the final candidate artifact.
- **Legal review**: a question that engineering evidence alone cannot settle.

## Initial Findings And Current Disposition

These are engineering gates, not legal conclusions.

### P0: Build the notice set from the final artifact

**Disposition: implemented as a checked contract; rerun against every final artifact.**

`THIRD_PARTY_NOTICES.md` alone is useful provenance, but it is not proof of a complete transitive
license closure for every release surface. Each workflow therefore derives an inventory from the exact
features, linked native library, WASM module, bundled JavaScript, fonts, and assets it ships. The
release must fail closed when a distributed component has no concluded license or required text.

### P0: Treat embedded KaTeX fonts as a separate licensed payload

**Disposition: implemented.** RaTeX and the KaTeX font payload have separate artifact scopes, OFL
text, font notice, hashes, and release projections.

The RaTeX code license does not cover the KaTeX font files. The dependency graph can embed
`ratex-katex-fonts` in render-capable artifacts. Artifact scopes and release projections include
the KaTeX notice plus OFL-1.1 text whenever the RaTeX font profile is selected.

### P0: Keep the ELK port and EPL evidence inseparable

**Disposition: engineering controls implemented; legal review remains.** The EPL-only crate
boundary, cargo-deny exception, full EPL text, source provenance, feature profiles, and artifact
projections are checked. Engineering cannot decide the remaining legal-review question.

The EPL-backed `merman-elk-layered` boundary is an architectural and compliance boundary. Any
artifact feature set that links it must carry EPL evidence. Before public binary publication, legal review
must confirm the chosen source-availability and notice mechanism for the source port.

### P0: Native binary archives need their own legal payload

**Disposition: implemented in release workflows; rerun against release candidates.**

An Apple zip, Android AAR/repository bundle, CLI archive, Python wheel, Flutter package, or VSIX is
not made compliant by a license file elsewhere in the Git repository. Archive-level assertions for
Merman license texts and applicable third-party materials now guard every release workflow.

### P1: Fix package metadata and packaged text mismatches

**Disposition: implemented.** VSIX uses `SEE LICENSE IN LICENSE` with complete projected text;
Flutter podspecs expose `MIT OR Apache-2.0`; and the Typst source/staging package is self-contained
and byte-verified.

- The VS Code manifest and packaged license were aligned to `SEE LICENSE IN LICENSE` plus the full
  projected project and third-party texts.
- The Flutter iOS and macOS podspecs now expose the package's dual-license choice.
- The Typst source package now contains its own legal bundle, and staged-package inventory is a
  checked, reproducible contract.

### P1: Complete file-level provenance for source ports

**Disposition: implemented in `THIRD_PARTY_COMPONENTS.json` and its fail-closed verifier.**

The machine-readable ledger records upstream repository, exact version/commit, upstream paths,
local paths, relationship (`copied`, `modified`, `translated`, `generated`, `linked`, `embedded`, or
`behavior-only`), concluded license, copyright, and required notice files. This is especially
important for Mermaid themes/icons, D3 curves, DOMPurify/sanitize-url behavior, Dagre/graphlib,
Cytoscape/FCoSE, Rough.js/rough-rs, venn/fmin, ZenUML, and ELK.

### P1: Preserve legal material in browser bundles and fixtures

**Disposition: runtime distribution implemented; fixture granularity remains a maintenance
control.** Playground deployment receives the canonical legal projection and an npm production
dependency report. The contract records fixture/source groups and local evidence, but new fixture
imports must continue to preserve group-level source commit/path evidence.

The Playground is not a registry package, but its deployed JavaScript is a distribution. Configure
the bundler to preserve or extract required license comments and publish a deterministic notice
file beside the assets. Separately, classify the large fixture corpus as `original`, `upstream
verbatim`, `upstream modified`, or `generated`; record source commit/path and license for each
upstream group, and prevent unknown fixtures from entering release archives.

## Medium-Priority Findings

### P2: Make license policy machine-readable

**Disposition: implemented with `deny.toml`, `about.toml`, the component contract, and generated
human-readable notices.**

The initial audit found no checked-in `cargo-deny`, `cargo-about`, or equivalent cross-ecosystem
policy. The current repository-owned controls define allowed expressions, selected branches for
`OR` expressions, named exceptions, exact legal files, and artifact-profile mappings. Human-readable
notices are generated from that policy rather than maintained independently.

The advisory policy keeps two narrow, documented exceptions for unmaintained transitive font
crates: `RUSTSEC-2026-0206` (`rustybuzz`) and `RUSTSEC-2026-0192` (`ttf-parser`). Current
`resvg`/`usvg`, `krilla`, and RaTeX releases provide no safe upgrade path yet. The exceptions must
be removed when those upstream stacks migrate; unrelated advisories and yanked dependencies still
fail the gate. `docs/security/RUSTSEC_EXCEPTIONS.json` records exact dependency paths, affected
artifact profiles, ownership, review dates, upstream issues, and exit conditions; its verifier
matches profile coverage by package version against every exact target closure. The reachable
`spin` dependency is pinned to the non-yanked `0.9.9` release.

### P2: Make every verifier inspect content, not filenames

**Disposition: implemented for checked-in projections and release workflows; final archives must
still be retained as release evidence.**

Several release checks establish that a file named `LICENSE` exists without proving that it contains
the selected Merman text or applicable third-party material. Hash or parse expected legal files,
extract every final archive, and compare its declared feature/profile manifest with the notice
closure. This applies especially to VSIX, npm WASM artifacts, Typst staging, wheels, AARs, and
XCFramework zips.

### P2: Separate build-tool licenses from shipped runtime licenses

**Disposition: implemented for npm production dependencies and named artifact feature scopes.
Cargo's normalized dependency report remains deliberately conservative for statically linked
native distributions.**

Raw npm and Cargo lockfile scans over-report build tools and can under-report bytes embedded by
generators or static linking. Record dependency kind and reachability from the final artifact.
For example, a private reference CLI package is not itself shipped, while KaTeX font bytes compiled
through RaTeX are shipped even without a JavaScript runtime dependency.

## Low-Priority Findings

### P3: Improve repository license discoverability

**Disposition: repository layout and README fixed; GitHub UI verification waits for the branch to
land.** The non-license root chooser was removed, while exact `LICENSE-MIT` and `LICENSE-APACHE`
texts remain.

Keeping only `LICENSE-MIT` and `LICENSE-APACHE` is a valid source layout for the declared choice, but
GitHub may not present a clean combined badge. Add a concise README licensing explanation and test
the GitHub Licenses API after release. Do not recreate a non-authoritative pointer solely to satisfy
the UI.

### P3: Trim non-product files from package candidates

**Disposition: package-content gates are implemented; size and content must still be reviewed for
each release candidate.**

Review `vsce ls`, `npm pack --dry-run`, crate listings, and Typst staging for test fixtures,
placeholder assets, stale generated output, or private reference material. This is primarily
packaging hygiene, but a smaller artifact also makes the legal inventory auditable.

The release gate must also create each archive, extract it into a fresh temporary directory, list

results. Dry-run output alone is not proof of archive content.

## Artifact Verification Checklist

Run these checks from a clean release tag and retain their outputs with the release evidence:

```text
Repository      Verify SPDX expressions; record exact commit; inspect GitHub detection only as UI.
Cargo           cargo package --locked --list -p <crate>; extract every generated .crate.
npm             npm pack --dry-run --json; npm pack; inspect tarball entries and WASM closure.
Python          python -m build; inspect sdist, each wheel METADATA, licenses/, and native payload.
Typst           build the publish profile; list the exact staged package; hash WASM and legal files.
Android         generate release POM/repository; unzip AAR and all attached artifacts.
Apple           unzip XCFramework release archive; verify checksum and adjacent legal materials.
Flutter         dart pub publish --dry-run after native injection; inspect every included binary.
VS Code         package each platform VSIX; run vsce ls; unzip and inspect licenses and executables.
```

For every artifact, record:

- artifact filename, SHA-256, release version, target, and build profile;
- source commit and lockfile digest;
- declared and concluded license expressions;
- complete file inventory and dependency/SBOM evidence;
- all bundled license/notice paths and their digests;
- reviewer, review date, unresolved questions, and legal-review decision where applicable.

Publication is blocked until every shipped artifact has a complete evidence record and no unresolved
P0 item applies to its contents.
